# Day 39: What is CI/CD? - Documentation

## Challenge Tasks & Core Concepts

### Task 1: The Problem with Manual Deployment
1. **What can go wrong?** Manual deployments introduce immense human error. An engineer might copy-paste the wrong command, miss a critical environment variable, run migrations in the wrong order, or accidentally deploy an outdated local code branch.
2. **The "It works on my machine" Problem:** This happens when code runs perfectly on a developer's laptop but breaks entirely when pushed to production. It occurs because the developer's local machine has unique dependencies, background tools, OS configurations, or environmental paths that do not exist on the live servers.
3. **Safe Manual Deploy Limit:** A standard development team can safely deploy manually maybe **1 to 2 times a week** before the coordination stress, testing fatigue, and risk of breaking things becomes unmanageable.

### Task 2: CI vs. CD vs. CD

#### 1. Continuous Integration (CI)
* **Definition:** Automatically building and running test suites every single time a developer pushes code changes to a shared repository branch to catch errors immediately.
* **Real-World Example:** When a developer opens a Pull Request on GitHub, automated scripts instantly check code formatting (`linting`) and execute unit tests.

#### 2. Continuous Delivery (CD)
* **Definition:** Ensuring that the main branch code is *always* in a deployable state and automatically updating staging/testing environments. However, releasing to actual production requires a final **manual approval (a human button click)**.
* **Real-World Example:** The pipeline builds the application and deploys it to a QA environment. The release manager manually reviews it and clicks an "Approve to Production" button.

#### 3. Continuous Deployment (CD)
* **Definition:** The complete removal of human intervention from the deployment lifecycle. If a code change successfully passes every automated test stage, it goes **live to production automatically**.
* **Real-World Example:** A engineer merges a spelling fix to `main`. The pipeline verifies it and automatically updates the public website live within 3 minutes.

### Task 3: Pipeline Anatomy
* **Trigger:** The exact event that tells the pipeline to start running (e.g., a `git push`).
* **Stage:** A major logical block of the pipeline (e.g., `Build`, `Test`, `Deploy`).
* **Job:** A specific unit of work within a stage that executes on an assigned runner.
* **Step:** Individual sequential commands or actions executed inside a single job.
* **Runner:** The clean virtual machine or container environment executing the pipeline actions.
* **Artifact:** The compiled or packaged output file generated by a job (e.g., a `.zip` file or a Docker image format).
